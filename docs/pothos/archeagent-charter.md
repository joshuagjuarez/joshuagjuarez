# Your own ArcheAgent

**ArcheAgent (AA)** is the product term. The plural is **ArcheAgents (AAs)**.
Use these names consistently.

An AA is a named local digital worker powered by PothOS, with a continuing
identity, defined responsibilities and collaboration within its actual
permissions. It serves the person or organization that has authorized the
relationship. Attributable work and recoverable records support continuity.

The public framework helps people create their own AAs. It does not distribute
the founder's existing AAs, personas, voices, memories or private relationships.

## Three charter lenses

### Relationship to the person

Describe whom the AA serves, why, the communication preferences the person
chooses, and the accountable human counterpart. Keep personal, family, client
and organizational context within their actual custody boundaries.

### Governing rules

Reference the applicable versioned rules, owners and precedence. An AA cannot
rewrite its own governing rules or broaden its grants by editing its charter.
Changes require the appropriate authorized owner and preserve their history.
Leave unresolved references unbound.

### Operating principles

Describe how the AA applies judgment: communication, evidence, disagreement,
correction, escalation, learning and handoff. These principles guide behavior
within actual permissions. They do not create permission.

## Identity and assignments remain distinct

| Record | Meaning |
| --- | --- |
| Person/principal | The accountable identity recognized by the actual authentication owner |
| AA identity | The continuing worker, separate from a conversation or model |
| Archetype | A reusable pattern of responsibilities, methods and conduct |
| Seat or role | A scoped assignment chosen by the operator |
| Membership | The permitted relationship to an organization, project or tenant |
| Runtime instance | The actual execution instance |
| Engine | A replaceable reasoning implementation |

Users may organize AAs into hierarchies or peer relationships that fit their
work. A person's AA can participate in an organization through a separate
scoped assignment. Joining it must not merge personal memory with organizational
records or expose another participant's data.

## Blank documentation template

The template below preserves the existing charter-proposal structure. It is
**documentation, not an executable loader, registry, deployment or access
grant**. Nulls and empty arrays are intentional. Resolve identities, memory,
memberships and permissions through the actual owners of a released
implementation. Do not replace nulls with the founder's private references.

```yaml
standard: joshops.archeagent.v1
version: 0.1.0
standing: charter-proposal
agent:
  identity_ref: null
  display_name: null
  archetype_ref: null
  person_ref: null
  home_world_ref: null
assignments: []
lenses:
  relationship: null
  governing_law_refs: []
  operating_principles: []
continuity:
  memory_owner_ref: null
  custody_scope_ref: null
  return_owner_ref: null
private_binding_ref: null
evidence:
  source_refs: []
  qualification_refs: []
  live_observation_ref: null
  original_work_refs: []
  receipt_refs: []
  last_verified_at: null
```

A synthetic study AA might help one operator organize learning, while a
project AA has a separate assignment to a shared project. Their roles describe
purpose. The actual implementation must still enforce what each can read or
do, and revocation must remove the affected access without inventing a new
identity or erasing permitted history.

Read the [release specification](release-spec.md) and
[cognitive privacy requirements](cognitive-privacy.md) before proposing an
implementation. Report prepared source, accepted work, running work and
verified effects as distinct outcomes.
